# v0.1.0 标准版本清单与发布门禁

> 状态：**仓库标准版本候选，可重复验证；生产业务可用仍为 No-Go。**
>
> 本清单不授权连接或修改生产服务器、云资源、安全组、DNS、证书、数据库、Secret 或 WorkBuddy 配置。

## 1. 两种“完成”必须分开

| 判定         | 含义                                                                                                      | v0.1.0 当前结论                                                     |
| ------------ | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 仓库标准版本 | 指定 Git commit 的锁文件、格式、Lint、类型、测试、构建、依赖审计、秘密扫描、SBOM 和源码哈希证据可重复生成 | 候选；只有干净 commit 上的 release workflow 全绿并保存证据后才是 Go |
| 生产业务可用 | 同一批签名 digest 已在 Staging 和 Production 通过真实外部依赖、TLS、数据恢复、监控和回滚验证              | **No-Go**                                                           |

仓库标准版本通过不自动提升为生产业务可用，也不能把“测试通过”“容器可构建”“HTTP 健康检查返回 200”写成“业务已上线”。

## 2. 可执行入口

在仓库根目录、Node.js 24 与 pnpm 11.19.0 下执行：

```text
pnpm install --frozen-lockfile
pnpm release:static
pnpm release:check
node scripts/quality/release-gate.mjs static --version 0.1.0
node scripts/quality/release-gate.mjs repository --version 0.1.0
node scripts/quality/release-gate.mjs evidence --version 0.1.0 --output <empty-output-directory>
node scripts/quality/release-gate.mjs verify --version 0.1.0 --evidence <output-directory>
node scripts/quality/release-gate.mjs production --version 0.1.0 --evidence <approved-production-evidence.json>
```

Windows 工作站没有 Docker CLI/Bash 时，可使用已从官方发行页取得并校验来源的独立 Compose 与 ShellCheck 二进制；CI 仍固定使用 `docker compose` 与 `bash -n`：

```powershell
$env:H5CS_DOCKER_COMPOSE_BIN = 'C:\path\to\docker-compose.exe'
$env:H5CS_SHELLCHECK_BIN = 'C:\path\to\shellcheck.exe'
$env:H5CS_API_ENV_FILE = (Resolve-Path infra/compose/api.env.example).Path
$env:H5CS_WORKER_ENV_FILE = (Resolve-Path infra/compose/worker.env.example).Path
$env:H5CS_MERCHANT_ENV_FILE = (Resolve-Path infra/compose/merchant-web.env.example).Path
$env:H5CS_OPS_ENV_FILE = (Resolve-Path infra/compose/ops-web.env.example).Path
node scripts/quality/release-gate.mjs repository --version 0.1.0
```

独立二进制只替换命令入口，不跳过 Compose 或 shell 校验；发布证据中应记录其版本与 SHA-256。

正式部署的四份服务环境文件字段清单分别在 [`api.env.example`](../../infra/compose/api.env.example)、[`worker.env.example`](../../infra/compose/worker.env.example)、[`merchant-web.env.example`](../../infra/compose/merchant-web.env.example) 和 [`ops-web.env.example`](../../infra/compose/ops-web.env.example)。它们不是可直接部署的配置：在服务器上分别创建受限文件，单独注入凭据；Worker 模型密钥不得进入 API/管理 Web，WorkBuddy 客户端密钥不得进入 Worker/管理 Web。

前两个 pnpm 命令是当前 v0.1.0 的固定别名；下面的直接 Node 命令用于生成、验证证据和执行生产硬门禁。

GitHub 的 `Repository release candidate` 手动运行默认只生成证据；只有获得镜像仓库发布授权并显式选择 `publish_images=true`，同时选择已获批准的 `web_path_mode=root` 或 `same_domain` 时，才会在证据通过后调用五镜像候选工作流推送到私有 GHCR。`undecided` 会阻断镜像任务，标签推送不再隐式发布镜像。候选镜像的产生不执行生产部署，也不改变本清单的生产 No-Go。

- `static`：检查版本一致性、Actions SHA 固定、常见秘密、禁止跟踪的凭据文件、WorkBuddy 连接器结构与自包含图标、发布文档和 `git diff --check`。结构检查不等于 WorkBuddy 实机或审核通过。
- `repository`：在 static 之上执行 high/critical 依赖审计、Compose 校验、格式、Lint、类型、全量测试、全量构建、Shell 语法和临时 SBOM/哈希证据生成。
- `evidence`：只接受干净工作树；生成 CycloneDX 1.6 `bom.cdx.json`、规范化依赖审计、逐文件 SHA-256、release manifest 和证据校验和。`--allow-dirty` 只用于开发验证，生成物明确标记 dirty，禁止发布。
- `verify`：重新计算证据包哈希，校验 SBOM 格式/组件数、manifest、锁文件以及 dirty 标记；上传或签名前必须通过。
- `production`：读取脱敏证据 JSON；任何必填项为 false、镜像缺失/未签名、审批不足或摘要格式错误时返回非零。

## 3. 仓库标准版本门禁

| 门禁             | 证据                                                                                                                       | 失败处理                                                                      |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 版本与工具链     | 根及所有声明版本的 workspace package 均为 `0.1.0`；`.nvmrc=24`；`packageManager=pnpm@11.19.0`                              | 停止，不创建 tag                                                              |
| 可复现安装       | `pnpm install --frozen-lockfile`                                                                                           | 停止；不得更新锁文件后绕过评审                                                |
| 秘密扫描         | `release-gate static`，并由 CI 在干净 checkout 重跑                                                                        | 任一命中都阻断；先吊销真实凭据，再清理历史                                    |
| 依赖审计         | `pnpm audit --audit-level=high` 与 `dependency-audit.json`                                                                 | high/critical 一律阻断；moderate/low 必须记录影响、暴露面、修复版本和复查日期 |
| 格式/Lint/类型   | `pnpm format:check`、`pnpm lint`、`pnpm typecheck`                                                                         | 任一失败阻断                                                                  |
| 全量测试/构建    | `pnpm test`、`pnpm build`                                                                                                  | 任一失败阻断；禁止仅挑选通过的包                                              |
| 基础设施静态校验 | dev/release 两份 Compose 均执行 `config --quiet`；release 的五个镜像引用必须为 `@sha256:`；所有已跟踪 `.sh` 执行 `bash -n` | 任一失败阻断；本机无 Docker 不是豁免，须由 CI/Linux 强制完成                  |
| SBOM             | CycloneDX 1.6；覆盖 production、development 和 optional 依赖                                                               | 空 SBOM、生成失败或与 manifest 哈希不一致时阻断                               |
| 制品完整性       | `source-files.sha256`、`release-manifest.json`、`evidence.sha256`                                                          | commit、版本、锁文件或任一文件哈希不一致时阻断                                |
| CI 供应链        | `.github/workflows` 的远程 Action 必须固定 40 位 commit SHA                                                                | 浮动 tag/branch 阻断                                                          |

## 4. 生产业务可用硬门禁

以下任一项缺失都必须保持 `productionBusinessReadiness=false`：

1. 五个部署单元的不可变 `sha256:` digest、签名验证和来源证明；Staging 与 Production 使用完全相同 digest。
2. 本阶段仅发布 Web 流程；WorkBuddy 接入暂停，公网网关必须对 MCP、OAuth 与 Skill 路径返回 404 并留存验证证据。日后启用 WorkBuddy 时另开接入验收，不复用本阶段的发布结论。
3. MySQL 的实际部署方案已获批准，TLS、最小权限、迁移、离机全量备份 + binlog PITR 和隔离恢复演练通过；3306 不得公网开放。2026-09-25 获批的单机例外仍须证明容量、故障域风险接受、持续离机备份和真实数据恢复，不能因容器健康或同盘空库恢复就视为通过。
4. 正式模型 Provider 与 Secret 管理已接通，真实生成冒烟通过，生产不允许 Mock/假成功回退；现有密钥已投递到服务器受限文件，但生产 Worker 在发布门禁通过前保持关闭。
5. `h5cs.1rying.com` 安装有效正式证书，HTTPS、HTTP→HTTPS 策略、安全头和自动续期测试通过；2026-09-27 HTTPS 维护入口与续期演练已通过，但业务路由尚未发布，不能标记 ready。
6. 真实 Staging 核心 E2E、租户隔离、SSE、异步 Job、文件处理和审计通过。
7. 告警真实送达值班渠道；previous 制品仍可获取；按 [发布与回滚 Runbook](../operations/release-and-rollback-runbook.md) 完成演练并验证业务。
8. 变更单、维护窗口、至少两名审批人和事故负责人齐全。

机器可读模板为 [production-readiness.example.json](production-readiness.example.json)。只能填写脱敏引用、摘要、布尔验收结果和审批标识；不得写 Token、Cookie、密码、私钥、连接串或预签名 URL。
