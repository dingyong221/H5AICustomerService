# H5 AI客服生成与管理平台：前端系统设计

> - 文档状态：V1.0 设计稿；本轮仅定义前端架构，不包含功能代码。
> - 需求依据：`H5_AI客服生成与管理平台_产品需求分析_V1.0.md`。
> - 适用范围：商家后台、消费者 H5、平台运营端。
> - 优先级说明：标记为 **P0** 的内容构成首版可试用闭环；标记为 **延期** 的内容不进入首版，但在模型和接口上保留扩展位置。

## 1. 设计目标与边界

### 1.1 目标

前端系统需要同时保证三件事：

1. 商家可以完成“创建草稿 → 补充知识 → 试聊 → 发布 → 获得固定链接 → 查看咨询 → 修正并再次发布”的闭环。
2. 消费者无需登录即可通过手机浏览器或微信内置浏览器进行连续咨询，并在有效凭据存在时刷新恢复、跨同源标签页同步。
3. 平台运营人员可以在严格权限与审计约束下管理商家、客服状态、模板、用量及异常。

前端不是数据隔离或权限判断的最终可信边界。所有商家、客服、Session、发布版本及会话内容的归属必须由服务端校验；前端只负责减少误操作、表达状态并提供必要的凭据。

### 1.2 最高优先级约束

- 公开客服标识只用于定位客服入口，不能用于读取会话或管理数据。
- 消费者会话凭据与公开标识分离；匿名凭据丢失时，不允许仅凭 `sessionId` 恢复历史。
- 编辑态与线上发布态分离；H5 固定地址不因发布、回滚而变化。
- 新 Session 使用当前正式版本；进行中的 Session 默认继续绑定创建时版本。
- 紧急暂停对所有 Session 立即生效，不受版本绑定影响。
- 同一 Session 的用户消息顺序提交，每次发送使用稳定的客户端请求标识，重试不得生成重复消息或重复用量。
- 失败、暂停、额度不足、知识处理中、发布冲突等均为显式业务状态，不能统一退化为“系统错误”。
- 不在浏览器中保存模型密钥、平台管理密钥或可跨商家使用的服务凭据。

### 1.3 本设计不负责

- 模型编排、RAG、知识切分与索引内部实现。
- 数据库、任务队列、部署拓扑和日志平台的内部选型。
- WorkBuddy Skill 包实现；Skill 与三个 Web 端共同依赖同一平台 API 契约。
- P2 真人坐席、订单、库存、预约、支付、退款等业务系统的实际集成。

## 2. 前端工程划分

### 2.1 推荐仓库结构

建议首版采用一个 TypeScript 单仓库、三个独立 Web 应用和少量共享包。共享编译、规范和契约，但三个应用独立构建与发布，避免运营端或商家端代码进入公开 H5 产物。

```text
apps/
  merchant-web/          商家后台，登录后使用
  consumer-h5/           消费者公开 H5，匿名访问，移动端优先
  ops-web/               平台运营端，独立权限与发布入口
packages/
  api-client/            由 OpenAPI 生成的类型、请求封装、错误解码
  domain-contracts/      仅放跨端稳定枚举、状态与无运行时副作用的类型
  design-tokens/         色彩、间距、字号、圆角、动效 token
  ui-admin/              商家端与运营端共享的后台基础组件
  ui-chat/               H5 聊天气泡、输入器、状态条等纯展示组件
  observability/         脱敏后的前端事件、错误与性能埋点
  test-utils/            MSW handler、fixture、无敏感数据的测试工厂
```

工程规则：

- `consumer-h5` 不得依赖 `ui-admin`、商家/运营路由、后台鉴权模块或后台 API client。
- `ops-web` 与 `merchant-web` 可以共享视觉基础，但不能共享包含权限假设的页面组件。
- `api-client` 按调用面拆分导出：`public`、`merchant`、`operator`，禁止用一个万能客户端绕过边界。
- 共享包只抽取已稳定且至少被两个应用复用的能力；页面级业务逻辑保留在各应用内。
- 三端统一错误协议、追踪 ID、日期与枚举定义，避免手写字符串漂移。

### 2.2 部署与地址建议

| 应用 | 建议地址 | 缓存策略 | P0 要点 |
| --- | --- | --- | --- |
| 消费者 H5 | `https://c.example.com/a/:publicSlug` | 带哈希静态资源长缓存；HTML 短缓存或不缓存；配置接口不被 CDN 错误长期缓存 | 固定入口、体积小、移动端优先 |
| 商家后台 | `https://console.example.com` | 静态资源长缓存；HTML 版本探测 | 登录态、草稿编辑、发布闭环 |
| 平台运营端 | `https://ops.example.com` | 独立发布、严格 CSP、禁止搜索引擎收录 | 不与商家后台仅靠隐藏菜单隔离 |

若首版受部署条件限制必须同域，也应使用独立入口、独立构建产物与服务端路由保护，而不是将运营页面打包进商家端后只做前端权限隐藏。

### 2.3 分层约定

每个应用内部采用轻量分层，不引入复杂前端领域框架：

```text
app/          启动、路由、全局 provider、全局错误边界
pages/        路由页面与页面级数据编排
features/     可独立测试的业务用例，如发布、发送消息、提交需求
entities/     Assistant、Release、Session、Message 等前端模型与展示
shared/       当前应用内部的请求、存储、组件和工具
```

依赖方向为 `app/pages → features → entities/shared`。页面通过查询与命令调用 API，不复制服务端规则成为第二套真相。

## 3. 商家后台设计

### 3.1 路由与页面

建议 URL 从一开始带 `assistantId`，即使 P0 是一商家一客服，也不把“唯一客服”固化进页面状态。

| 路由 | 页面 | P0 内容 | 主要状态 |
| --- | --- | --- | --- |
| `/login` | 登录 | 登录、过期返回、账号找回入口 | 未登录、提交中、凭据错误、锁定/禁用 |
| `/onboarding` | 商家档案与首次创建 | 商家名称、业务描述、客服基础信息、生成结构化草稿 | 分步草稿、缺失项、生成中、生成失败 |
| `/` | 工作台 | 客服状态、公开入口、待处理咨询、知识状态、用量概况 | 未创建、草稿、可发布、已发布、暂停、额度不足 |
| `/assistants/:assistantId/settings` | 创建及设置 | 基础信息、范围、风格、模式、页面、服务设置 | 已保存、未保存、自动保存失败、版本冲突 |
| `/assistants/:assistantId/knowledge` | 知识库 | FAQ、文本、PDF、来源、有效期、处理状态 | 待上传、上传中、待处理、处理中、可用、失败 |
| `/assistants/:assistantId/test-release` | 测试与发布 | 试聊、测试问题、发布前检查、版本差异、发布、回滚 | 草稿不可发布、索引未就绪、测试中、发布中、冲突、成功 |
| `/assistants/:assistantId/share` | 访问入口 | 固定链接、复制、二维码、手机预览 | 已发布、未发布、暂停 |
| `/conversations` | 咨询列表 | 筛选、未解决、需求、跟进状态 | 加载、空、部分失败、无权限 |
| `/conversations/:sessionId` | 咨询详情 | 消息、摘要、需求字段、关联版本、问题原因、知识草稿入口 | 正常、内容已删除/脱敏、无权限 |
| `/account` | 账号与服务 | 商家资料、联系渠道、额度、数据保留信息 | 正常、保存中、冲突 |

`/assistants` 列表在 P0 可省略或只做内部跳转；数据模型和导航上下文仍保留多客服能力。多客服管理页面属于延期项。

### 3.2 导航与信息架构

P0 主导航建议为：工作台、客服设置、知识库、测试与发布、咨询管理、账号与服务。分享入口同时出现在工作台与发布成功结果中，不需要成为高频一级菜单。

创建流程不设计成一次性不可返回的长向导。首次使用以步骤引导进入同一组正式编辑页面，商家中途退出仍保存服务端草稿；再次进入时从缺失项继续。

### 3.3 草稿编辑状态

前端区分三类数据：

- `serverDraft`：最近一次服务端确认的草稿，带 `revision` 或 `etag`。
- `formDraft`：当前页面内尚未确认保存的字段。
- `publishedSnapshot`：只读的当前线上版本，用于差异比较，不能直接编辑。

保存命令携带 `revision` 与稳定 `idempotencyKey`。遇到版本冲突时不得覆盖服务端内容，应拉取最新草稿并展示“重新加载 / 对比后重试”；P0 至少提供重新加载和保留本地文本供复制，精细字段级合并可延期。

自动保存策略：

- 文本输入停止约 800–1200ms 后保存；选择、开关等明确动作可立即保存。
- 页面离开前如仍有未提交命令，展示阻止导航提示。
- 浏览器本地草稿只用于防止意外刷新，不作为权威版本；只保存普通配置，不缓存上传文件、联系方式或会话内容。
- 服务端保存成功后清理对应本地恢复副本。

### 3.4 知识库交互

知识条目使用有限状态机展示：

```text
local_selected → uploading → queued → processing → ready
                         ↘ upload_failed
                                  queued/processing → process_failed → retrying
```

- 只有服务端返回的 `ready` 条目才能参与待发布版本。
- 关闭页面不取消已提交的处理任务；返回页面后重新查询状态。
- P0 使用短轮询获取 PDF 处理状态，页面不可见时降低频率或暂停；WebSocket 任务推送延期。
- 失败卡片展示可理解原因、追踪 ID、重试或删除入口，不以“可用”乐观呈现。
- 删除或修改已发布知识实际生成新草稿；界面明确说明线上版本尚未改变。
- 上传前检查扩展名、MIME、大小只是体验优化，服务端仍需重新校验。

### 3.5 测试、发布与回滚

发布页由四部分构成：

1. 发布前检查：必填信息、至少一项可用知识、无法回答策略、索引就绪、联系渠道一致性。
2. 隔离试聊：使用草稿及草稿知识版本，不写入正式消费者咨询列表和正式用量口径；界面持续显示“测试会话”。
3. 版本差异：按配置、知识来源和页面外观分组，避免只展示原始 JSON。
4. 发布动作：二次确认，提交指定草稿 revision，服务端成功后再显示“已发布”和链接。

发布、回滚都是异步命令。按钮提交后以服务端任务状态为准；浏览器断开后可凭 `operationId` 恢复结果。超时不能被显示为成功。若服务端返回 `accepted/processing`，页面显示进行中并轮询，直到 `succeeded` 或 `failed`。

紧急暂停与普通编辑分开：暂停命令从工作台和发布页都可触达，明确提示其会立即影响所有 Session；恢复服务同样需要确认。暂停不创建新的普通发布版本。

### 3.6 咨询管理

- 会话列表以服务端游标分页，筛选条件编码进 URL，便于刷新和返回。
- 列表默认只显示业务必要摘要，不在表格中铺开展示手机号等联系方式。
- 详情页显示消息原始顺序、失败状态、摘要、已提取需求、关联 `releaseId`、未解决原因及来源。
- 商家可修改“待处理 / 处理中 / 已处理”人工跟进状态；不得编辑消费者原始消息。
- “生成知识草稿”只生成待确认内容，并带回来源会话，不能一键成为线上知识。
- 已按保留策略删除的内容显示删除占位和时间，不尝试从浏览器缓存恢复。

## 4. 消费者 H5 设计

### 4.1 路由与视图

消费者端以单页为主，保持入口简洁：

| 路由 | 视图 | 说明 |
| --- | --- | --- |
| `/a/:publicSlug` | 聊天主页 | 加载公开配置，创建或恢复该入口下的有效 Session |
| `/a/:publicSlug/request` | 需求提交 | 可实现为同路由全屏弹层；URL 化便于刷新恢复表单结构，不保存敏感输入 |
| `/a/:publicSlug/privacy` | 隐私与用途说明 | 展示当前商家的收集用途、联系渠道和平台必要说明 |

未知、下架或无权访问的 `publicSlug` 使用专门的入口不可用页，不调用 Session 恢复接口。

### 4.2 启动流程

```text
读取 publicSlug
  → 获取公开客服配置与当前服务状态
  → 读取该客服对应的匿名访客凭据引用
  → 请求“恢复或创建有效 Session”
  → 获取 session capability、release 摘要、消息游标
  → 拉取历史消息并进入 ready
```

关键原则：

- 不由前端自行决定某个旧 `sessionId` 是否仍有效；调用服务端的恢复/创建接口裁决。
- 本地按 `publicSlug` 或稳定 `assistantPublicId` 隔离存储，不允许切换商家后复用 Session。
- 服务端返回的会话访问 capability 是读取历史的必要条件；公开链接本身不是凭据。
- capability 优先放在 `Secure`、`HttpOnly`、合适 `SameSite` 的 cookie 中；若因跨域部署确需 JS 可读 token，应使用短期、仅限单一访客/客服的令牌，并禁止进入 URL、日志和埋点。
- 初始化期间输入器禁用，并使用骨架屏避免先接受输入后再切换 Session。

### 4.3 消费者会话状态模型

会话模型由相互正交的状态组成，避免用一个 `loading` 覆盖全部行为：

```ts
type SessionLifecycle =
  | 'booting'
  | 'active'
  | 'expired'
  | 'ended'
  | 'unavailable';

type ServiceAvailability =
  | 'online'
  | 'paused'
  | 'quota_exhausted'
  | 'rate_limited'
  | 'assistant_unpublished'
  | 'platform_degraded';

type OutgoingStatus =
  | 'queued'
  | 'submitting'
  | 'accepted'
  | 'streaming'
  | 'completed'
  | 'failed_retryable'
  | 'failed_final'
  | 'cancelled';
```

最小前端状态建议：

```ts
interface ConsumerSessionState {
  publicAssistant: PublicAssistantProfile;
  session: {
    id: string;
    releaseId: string;
    lifecycle: SessionLifecycle;
    lastActivityAt: string;
    nextMessageCursor?: string;
  } | null;
  availability: ServiceAvailability;
  messages: MessageView[];
  composer: { text: string; clientRequestId?: string };
  leadDraft: Record<string, unknown>;
  sync: { leaderTabId?: string; lastEventSeq: number };
}
```

`leadDraft` 只在提交页面内存中维护；包含联系方式时默认不写入 `localStorage`。需求提交成功后依赖服务端返回的 `leadId` 和幂等结果清空表单。

### 4.4 消息模型与乐观显示

每条用户消息在前端创建 `clientRequestId`（UUID），并以此作为重试键：

```ts
interface MessageView {
  localKey: string;
  messageId?: string;
  clientRequestId?: string;
  role: 'user' | 'assistant' | 'system_notice';
  content: string;
  status: OutgoingStatus | 'persisted';
  serverSeq?: number;
  createdAt?: string;
  error?: ApiProblem;
}
```

- 用户点击发送后可以立即显示本地消息，但标记为“发送中”，不将其视为服务端已保存。
- 重试复用原 `clientRequestId`，不可生成新的请求 ID。
- 以服务端 `serverSeq` 作为最终顺序；客户端时间只用于临时显示。
- 助手流式内容先作为临时消息展示，完成事件携带正式 `messageId`、`serverSeq` 和完成原因。
- 流中断后先查询该请求的服务端结果；确认未完成才允许重试，避免重复生成。
- 失败助手消息不进入前端“已完成上下文”假设；后续是否可发送由服务端 Session 状态裁决。

### 4.5 流式会话协议

P0 推荐 `fetch + ReadableStream` 的服务端流式响应，事件内容采用 SSE 格式或 NDJSON。与原生 `EventSource` 相比，它可使用 POST body 发送消息、携带幂等键，并能明确处理 HTTP 错误。WebSocket 不作为首版必需项。

建议一次发送的事件序列：

```text
message.accepted      用户消息已落库，返回 messageId 与 serverSeq
assistant.started     助手消息占位与 traceId
assistant.delta       追加文本片段，带递增 eventSeq
assistant.completed   返回正式消息、finishReason、用量摘要（不暴露内部提示词）
session.updated       可选，需求状态或最后活动时间更新
error                 结构化可重试/不可重试错误
```

协议要求：

- HTTP 请求头携带 `Idempotency-Key: clientRequestId`；服务端用 Session + key 去重。
- 每个流事件带单调递增 `eventSeq`，客户端忽略重复序号。
- 使用 `TextDecoder` 增量解码，处理 UTF-8 字符跨 chunk 边界，不假设一个网络 chunk 等于一个事件。
- 用户主动离开或新建咨询时使用 `AbortController` 终止 UI 消费；终止连接不等同于撤销服务端已接受的消息。
- 浏览器回到前台或网络恢复后，通过“按请求 ID 查询结果”或“从消息游标补拉”收敛到服务端状态。
- 首段超时、总时长超时和无数据心跳超时分别处理；出现超时时展示可理解提示与追踪 ID。
- 同一 Session 同一时刻只允许一个待处理用户消息。输入器在 `submitting/accepted/streaming` 期间禁用；P0 不提供排队多发。

### 4.6 Session 恢复

#### 刷新与短暂离开

恢复接口返回以下之一：

| 结果 | 前端行为 |
| --- | --- |
| `resumed` | 拉取当前 Session 消息；如存在进行中请求，查询或订阅其结果 |
| `created` | 显示欢迎语，创建全新咨询 |
| `expired_and_created` | 显示“已开始新的咨询”通知，不继承旧需求 |
| `credential_invalid` | 清除本地无效引用，创建新访客和 Session，不泄露旧历史 |
| `paused/unavailable` | 展示服务状态；根据服务端策略可只读恢复历史，但禁用发送 |

若刷新发生在流式回复期间，重载后不得仅凭本地半截文本继续拼接；前端应以服务端持久消息或请求状态为准替换临时内容。

#### 主动新建咨询

“新建咨询”需要确认“当前上下文将结束”。提交带幂等键的结束并新建命令，成功后再清空消息视图。失败时保留原 Session，不提前清空。新 Session 不继承原需求状态；历史是否仍可只读查看由产品另行确认，P0 可直接从当前视图移除但不得删除服务端记录。

#### 超时

30 分钟无互动是建议基线，不在前端用计时器自行强制结束。用户下一次提交时由服务端判断：若过期，返回新 Session 和明确结果，前端把原本待发送的文本带到新会话并要求用户再次确认发送，避免无提示地改变上下文后直接提交。

### 4.7 多标签页同步

P0 采用 `BroadcastChannel`，不支持时回退到同源 `storage` 事件。同步内容只包含无敏感正文的控制事件：

```text
SESSION_SELECTED(sessionId, releaseId)
MESSAGE_ACCEPTED(clientRequestId, serverSeq)
STREAM_OWNER(tabId, clientRequestId, leaseUntil)
MESSAGES_INVALIDATED(afterSeq)
SESSION_ENDED(sessionId)
AVAILABILITY_CHANGED(status)
```

正文由其他标签通过 API 重新拉取，避免将消费者消息广播并持久化到浏览器存储。

并发策略：

- 同一 Session 选举一个当前发送标签（短租约 + 心跳）；其他标签显示“此咨询正在另一页面回复”，输入器暂时只读。
- 若两个标签几乎同时发送，服务端仍以 Session 顺序锁和幂等规则为最终裁决，后提交者得到 `session_busy`。
- 流 owner 关闭或租约过期后，其他标签不能续接原网络流，只能查询请求结果并恢复展示。
- 收到 `SESSION_ENDED` 后各标签立即停止向旧 Session 发送，并调用恢复接口获得新状态。

SharedWorker 可更严格复用连接，但微信与部分 WebView 兼容性不稳定，列为延期方案。

### 4.8 错误、暂停与退化状态

| 状态 | 用户表达 | 可用操作 | 是否自动重试 |
| --- | --- | --- | --- |
| 离线 | “网络不可用，内容尚未发送” | 保留输入、手动重试 | 网络恢复后只做状态查询，不自动重新发送业务消息 |
| 请求超时 | “回复等待时间较长，可检查结果或稍后重试” | 查询结果、重试 | 先查询请求状态 |
| 流中断 | 保留已显示片段并标“回复未完成” | 恢复结果、重试 | 自动补拉一次可接受 |
| 限流 | “请求较多，请稍后再试” | 倒计时后重试 | 遵循 `Retry-After`，不循环重试 |
| 商家额度不足 | “当前暂时无法继续 AI 咨询” | 联系商家 | 不自动重试 |
| 客服暂停 | 展示商家自定义暂停说明 | 联系商家、只读历史（若允许） | 不自动重试 |
| 客服未发布/下架 | 入口不可用页 | 联系商家（若公开配置允许） | 不自动重试 |
| Session 过期 | “已开始新的咨询” | 确认后发送原草稿 | 不向旧 Session 重试 |
| 内容被拒绝 | 提示该条内容无法处理 | 修改输入 | 不原样自动重试 |
| 平台故障 | 通用故障说明 + 追踪 ID | 稍后重试、联系商家 | 有上限的只读状态查询 |

禁止无限指数重试模型调用；禁止将暂停、额度不足或内容拒绝伪装为普通网络失败。

### 4.9 移动端与微信兼容

P0 兼容目标建议在技术评审后固化为最近两个主版本的 iOS Safari、Android Chrome，以及当前主流微信 iOS/Android WebView。实际支持矩阵以真机测试结果为准。

布局与输入：

- 使用 `100dvh` 并为不支持动态视口单位的环境提供 `visualViewport`/CSS 变量回退，避免软键盘遮挡输入器。
- 适配 `env(safe-area-inset-top/bottom)`，底部输入器与 iPhone 安全区不重叠。
- 消息区采用稳定滚动容器；只有用户接近底部时自动跟随流式内容，用户上滚后显示“回到底部”，不抢滚动位置。
- 输入框字号至少 16px，防止 iOS 聚焦自动缩放；触控目标至少约 44px。
- 中文输入法 composition 期间 Enter 不发送；避免微信下拉刷新与聊天上滚冲突。
- 单条长文本和长 URL 可换行；流式 Markdown 未完成时使用纯文本增量显示，完成后再做安全渲染。

微信环境：

- 不依赖第三方 cookie、Service Worker 或 SharedWorker 才能完成核心咨询。
- 复制链接、保存二维码、拨号和打开企业微信等能力做特性检测，并提供普通链接或长按保存回退。
- 首版不强依赖微信 JSSDK；只有确认需要定制分享卡片等能力时再接入签名流程。
- 页面前后台切换监听 `visibilitychange`，回到前台后补拉会话状态。
- 禁止使用 `window.opener`、URL token 或非 HTTPS 传递会话凭据。

可访问性与弱网：

- 流式回复区域使用克制的 `aria-live` 策略，避免每个 token 都触发读屏；完成后统一播报。
- 状态不能只靠颜色表达；错误、发送中、暂停均有文字和图标。
- 静态外壳尽量小，首屏不加载后台组件、图表、富文本编辑器；次要弹层按需加载。
- 网络差时先显示商家身份、AI 标识、暂停/可用状态和输入器，再加载更早历史。

## 5. 平台运营端设计

### 5.1 路由与页面

| 路由 | 页面 | P0 内容 |
| --- | --- | --- |
| `/login` | 运营登录 | 独立运营身份认证、会话过期处理 |
| `/` | 运营概览 | 商家/客服状态、用量、失败任务与告警摘要 |
| `/merchants` | 商家管理 | 状态、额度、创建时间、筛选；不默认展示消费者内容 |
| `/merchants/:merchantId` | 商家详情 | 客服与发布状态、用量、异常、可审计的操作入口 |
| `/assistants/:assistantId` | 客服详情 | 正式版本、暂停状态、知识任务概览、公开入口检查 |
| `/templates` | 行业模板 | 模板列表与版本；P0 可仅限平台预置模板管理 |
| `/usage` | 用量管理 | 按商家与时间查看聚合用量、人工调整试点额度 |
| `/failures` | 失败与任务 | 知识处理、发布、模型调用等异常查询 |
| `/audit` | 审计 | 运营敏感操作和消费者内容访问记录 |

### 5.2 权限与敏感操作

- 菜单和按钮按服务端返回的 capability 显示，但每次 API 调用仍由服务端鉴权。
- 查看消费者会话正文不是商家详情的默认能力；需要业务理由、相应权限并记录审计。
- 暂停商家、调整额度、访问会话正文等敏感动作需要确认对话框，展示影响范围和原因字段。
- UI 不提供“切换为任意商家”绕过审计的万能模式；如需代操作，应使用受审计、限时的服务端授权机制。
- 批量导出消费者消息、批量商家操作和自定义角色配置均延期，避免首版扩大数据泄露面。

### 5.3 大列表与运营效率

P0 使用服务端筛选、排序和游标分页。筛选条件写入 URL；表格列由稳定字段组成，联系方式、消息正文等敏感信息不参与通用搜索。运营动作返回异步 `operationId` 时采用任务状态查询，与商家端发布任务使用一致交互模型。

## 6. 前端状态管理原则

### 6.1 状态分类与工具

| 状态类型 | 示例 | 推荐归属 |
| --- | --- | --- |
| 服务端状态 | 客服配置、知识列表、消息、用量、任务状态 | TanStack Query 缓存，服务端为真相 |
| 表单状态 | 配置编辑、FAQ、需求提交 | React Hook Form + Zod；敏感表单不持久化 |
| 有限状态机 | H5 会话启动/发送/流式/恢复，发布流程 | 显式 reducer；复杂度上升后再引入 XState |
| URL 状态 | 列表筛选、分页游标、当前标签 | Router search params |
| 短期 UI 状态 | 弹层、折叠、toast | 组件本地状态 |
| 跨标签同步 | Session 变更、消息失效、流 owner | BroadcastChannel + 服务端收敛 |

P0 不建议引入全局 Redux 存放所有服务端数据。若需要跨页面的客户端全局状态，优先使用小型 Zustand store，且禁止在其中长期保存会话正文或后台敏感数据。

### 6.2 查询缓存规则

- Query key 必须包含资源边界，例如 `['merchant', merchantId, 'assistant', assistantId]`；不能只有通用 `['assistant']`。
- 退出登录或商家上下文变化时销毁对应 QueryClient 缓存，而非仅跳转页面。
- 消费者端切换 `publicSlug` 时创建新的会话作用域并清空旧消息内存。
- 默认不把 Query cache 持久化到浏览器；离线历史浏览不属于 P0。
- mutation 成功后按精确 key 失效，避免全站重复拉取和跨租户短暂串显。

### 6.3 结构化错误模型

API 使用统一 Problem Details 风格：

```ts
interface ApiProblem {
  type: string;
  title: string;
  status: number;
  code:
    | 'validation_failed'
    | 'unauthenticated'
    | 'forbidden'
    | 'not_found'
    | 'revision_conflict'
    | 'session_expired'
    | 'session_busy'
    | 'assistant_paused'
    | 'quota_exhausted'
    | 'rate_limited'
    | 'content_rejected'
    | 'operation_failed'
    | 'service_unavailable';
  traceId: string;
  retryable: boolean;
  retryAfterSeconds?: number;
  fieldErrors?: Record<string, string[]>;
}
```

前端根据稳定 `code` 决定行为，不解析自然语言错误。展示文案由前端本地化资源或服务端安全的用户文案提供；服务端堆栈、模型原始错误和内部提示词不得下发。

## 7. 设计系统

### 7.1 两类体验、一套基础 token

后台与消费者 H5 使用同一基础 token（颜色语义、字号、间距、圆角、阴影、动效时长），但保留两套组件密度：

- `ui-admin`：桌面优先、信息密度中等，支持表单、表格、筛选、步骤、状态标签和版本差异。
- `ui-chat`：移动端优先、大触控目标、强品牌可配置，支持消息、输入器、快捷问题、服务状态、联系入口和需求表单。

不直接让商家任意输入 CSS。主题仅开放受控字段，如主色、头像、欢迎语、快捷问题；前端根据主色计算或选择可读前景色，并进行对比度校验。失败时使用系统安全色或提示商家调整。

### 7.2 核心语义组件

P0 组件清单：

- `StatusBadge`：草稿、发布、知识处理、会话跟进等不同状态域使用显式映射。
- `AsyncActionButton`：防重复提交、进度、结果与追踪 ID。
- `ProblemNotice`：验证错误、可重试故障、不可操作状态分层表达。
- `ReleaseDiff`：配置、知识、页面设置的语义差异。
- `KnowledgeItemCard`：来源、有效期、状态、失败原因和重试。
- `ChatMessage`、`StreamingMessage`、`Composer`、`QuickQuestions`。
- `ServiceStatusBanner`：暂停、额度不足、限流、平台退化。
- `LeadForm`：字段用途、可选联系方式、提交结果。
- `EmptyState`、`Skeleton`、`ConfirmImpactDialog`。

### 7.3 安全渲染

- 助手回复默认支持受限 Markdown：段落、列表、强调、链接；禁止原始 HTML、脚本、iframe 和内联事件。
- 外部链接增加 `rel="noopener noreferrer"`，并对不可信协议进行过滤。
- 电话、企业微信等联系渠道来自已发布配置的结构化字段，不从模型回复中解析成特权动作。
- 富文本预览和二维码内容均使用固定公开 H5 URL，不允许把匿名会话 token 编码进二维码。

## 8. API 边界与前端契约

### 8.1 API 调用面

建议服务端对三个调用面进行明确路径或网关隔离：

| 调用面 | 示例前缀 | 身份 | 前端可访问资源 |
| --- | --- | --- | --- |
| Public API | `/api/v1/public` | 匿名访客 capability | 公开客服配置、自己的 Session/消息/需求 |
| Merchant API | `/api/v1/merchant` | 商家登录身份 | 本商家的草稿、知识、发布、咨询、用量 |
| Ops API | `/api/v1/ops` | 运营身份与岗位权限 | 商家状态、额度、任务、模板、审计 |

跨域时需要精确 CORS allowlist、凭据策略和 CSRF 防护；不允许 `*` 与凭据并用。若同域部署，仍保留逻辑调用面与独立鉴权中间件。

### 8.2 P0 端点能力清单

以下是前端所需能力，不限定最终 REST 路径命名：

**Public**

- 按 `publicSlug` 获取公开资料、主题、欢迎语、快捷问题、联系入口与服务可用状态。
- 恢复或创建访客/Session；获取当前 Session 元数据。
- 按游标读取自己的消息；按 `clientRequestId` 查询发送结果。
- 发送消息并接收流式事件。
- 结束并新建咨询。
- 幂等提交需求；读取提交结果。
- 提交“无帮助”等有限反馈。

**Merchant**

- 获取/更新商家档案、客服草稿与服务设置，支持 revision 冲突检查。
- 生成结构化配置草稿并返回事实缺失项，不直接发布。
- 创建 FAQ/文本知识；申请上传并完成 PDF 上传；查询处理任务；重试/删除。
- 创建隔离测试会话、发送测试消息、读取测试结果。
- 获取发布前检查、版本差异；发布、回滚、查询 operation。
- 暂停/恢复；获取固定链接与二维码内容。
- 查询会话、消息、摘要、需求、未解决原因；更新人工跟进状态；生成知识草稿。
- 获取用量与额度状态。

**Operator**

- 查询商家、客服、发布版本、任务失败和聚合用量。
- 按权限调整商家状态、暂停状态和试点额度。
- 管理 P0 行业模板版本。
- 创建会话内容访问审计并在授权后读取必要内容。
- 查询敏感操作审计记录。

### 8.3 通用契约规则

- OpenAPI 是普通 JSON API 的契约源；流式事件额外提供可机器校验的 schema 和录制样例。
- 所有写请求支持幂等键；更新资源同时支持 revision/ETag 条件写。
- 时间均为带时区的 ISO 8601；前端展示时按用户时区格式化。
- 列表使用游标分页；不以大 offset 扫描会话和消息。
- 删除、暂停、发布、额度调整等响应返回真实最终状态或 `operationId`，不使用模糊 `success: true`。
- 客服/知识/会话/消息响应带稳定 ID；前端不从名称或数组位置推断身份。
- API 返回安全、稳定的错误 code、是否可重试与 `traceId`。
- 上传采用服务端申请的受限直传地址或平台流式上传；文件解析状态通过知识任务查询，浏览器不承担 PDF 文本提取。
- 首版轮询采用服务器建议的 `pollAfterMs`，页面进入后台后降频；避免每个列表行独立轮询。

### 8.4 版本兼容

- 三端静态资源发布与 API 版本解耦；服务端在 P0 周期内保持向后兼容。
- 应用启动时可读取 `buildId` 与最低支持版本。检测到不可兼容版本时提示刷新，不在用户流式回复过程中强制刷新。
- schema 新增字段默认向后兼容；枚举出现未知值时用“未知状态”安全降级并上报，而不是页面崩溃。

## 9. 前端安全与隐私基线

- 后台优先使用 HttpOnly 安全 cookie；对 cookie 鉴权写操作加入 CSRF 防护。
- 严格 CSP，生产环境禁用任意内联脚本和 `eval`；只允许必要 API、对象存储和监控域名。
- React 文本渲染保持转义；Markdown 经 allowlist sanitizer 处理。
- Token、手机号、消息正文、上传文件名等不得进入 URL、前端监控 breadcrumb 或普通 analytics。
- 退出登录、账号切换、商家切换时清理内存缓存、本地恢复草稿和跨标签频道。
- 运营端设置更短空闲会话时长；商家端与运营端均处理服务端主动失效。
- H5 的本地存储只保存匿名凭据引用、当前入口和非敏感 UI 偏好；任何凭据范围必须被服务端限制到单一访客及客服。
- 前端 source map 上传到受控监控平台，不公开部署可直接下载的源映射。
- 埋点对 `publicSlug`、merchantId 等业务标识采用受控字段；不采集输入框内容和助手全文。

## 10. 可观测性与前端指标

三个应用统一记录：`app`、`buildId`、页面、匿名 trace/session 哈希、请求 `traceId`、耗时、错误 code 和网络状态。禁止记录原始会话正文、联系方式、访问 token 和模型内部信息。

P0 前端指标：

- H5 配置加载成功率、Session 恢复/新建成功率。
- 消息接受成功率、首个流事件耗时、首个文本片段耗时、完整回复耗时、流中断率。
- 重试率、重复请求被服务端去重数量、`session_busy` 发生率。
- 发布前检查失败分布、发布/回滚成功率、知识处理前端可见失败率。
- 页面 JS 错误率、资源加载失败率、Web Vitals 和不同微信/浏览器版本分布。

性能建议目标“首段回复 P95 不超过 5 秒”需要区分前端网络/建连、服务端排队、检索与模型首 token；前端埋点应记录分段时间，但最终口径由端到端 trace 关联确定。

## 11. 测试策略

### 11.1 测试金字塔

| 层级 | 工具建议 | P0 覆盖 |
| --- | --- | --- |
| 静态检查 | TypeScript、ESLint、Prettier、依赖边界规则 | 类型、无障碍基础规则、三端禁止依赖 |
| 单元测试 | Vitest | reducer、错误映射、流解析器、滚动判断、幂等 ID 保持、主题对比度 |
| 组件测试 | Testing Library + MSW | 表单校验、知识状态、发布检查、聊天发送/失败/重试 |
| 契约测试 | OpenAPI schema + 流事件 fixtures | 客户端生成不漂移、错误 code、未知枚举降级、UTF-8 分块 |
| 浏览器 E2E | Playwright | 三端关键闭环、多上下文隔离、多标签页、刷新恢复、弱网与流中断 |
| 真机兼容 | iOS Safari、Android Chrome、微信 iOS/Android | 键盘、滚动、安全区、前后台、复制/二维码、长回复 |

### 11.2 必测前端场景

对需求 A01–A14 的前端重点覆盖如下：

| 验收 | 前端自动化/验证点 |
| --- | --- |
| A01 | 生成结果进入可编辑草稿；缺失事实以待补充显示，不能预填虚构价格 |
| A02 | PDF 失败明确原因、状态不为可用、重试后任务状态可恢复 |
| A03 | 发布任务真实成功后才显示固定链接；重复点击/刷新不重复发布 |
| A04 | 越界、资料不足的服务端结果被正确展示，联系入口与配置一致 |
| A05 | 同 Session 发送“周六呢”时沿用当前 Session，刷新后仍恢复消息顺序 |
| A06 | 两个独立浏览器上下文各自只能看到自己的消息与需求 |
| A07 | 修改 publicSlug/sessionId/token 的负向 E2E 不显示其他商家数据 |
| A08 | 刷新恢复；新建咨询确认；过期后不携带旧需求，草稿需再次确认发送 |
| A09 | 旧 Session 显示其绑定版本，新 Session 使用新版本；固定 URL 不变 |
| A10 | 需求双击/重试只产生一个结果；无坐席时不出现“转接成功” |
| A11 | 超时、暂停、额度不足、限流均有不同 UI 和合法操作 |
| A12 | 前端 API 契约与 Skill 共用平台契约；H5 不依赖 WorkBuddy 在线 |
| A13 | 相同 `clientRequestId` 重试不产生重复消息；同 Session 并发显示 busy 并收敛 |
| A14 | XSS Markdown、越权 API、配置注入和敏感日志的负向测试 |

### 11.3 流式与多标签专项

流解析器必须用人为切割的 chunk 测试：一个汉字跨字节、一个事件跨多个 chunk、多个事件同 chunk、重复 `eventSeq`、完成前断流、错误事件后仍有脏数据。E2E 使用可控 mock server 延迟每个事件并模拟网络中止。

多标签测试至少覆盖：

- 标签 A 流式回复时标签 B 禁止发送并能补拉完成结果。
- A 在流中关闭，B 等租约过期后查询结果而非重复发送。
- A 主动新建咨询，B 收到结束事件后不再向旧 Session 发送。
- 两标签竞争发送时服务端只接受一个，另一个明确显示 `session_busy`。

### 11.4 发布门禁

P0 合并与发布门禁：类型检查、lint、单元/组件测试、OpenAPI 兼容检查、三端关键 E2E、依赖与包体积预算。消费者 H5 需额外检查首屏资源预算和无后台代码泄入；运营端需额外检查路由鉴权及敏感信息埋点扫描。

## 12. 推荐技术栈

以下选型服务于 4–7 周小规模试点，优先成熟、可测试与团队易维护；具体版本在开工时锁定并完成安全评估。

| 类别 | 推荐 | 理由 |
| --- | --- | --- |
| 语言/构建 | TypeScript、Next.js、pnpm workspace | 与总体架构保持一致；三个应用独立构建，共享类型和工具，支持静态外壳、SPA 交互及后续按需服务端渲染 |
| UI 框架 | React | 生态成熟，适合后台表单与流式 H5；团队若已有 Vue 3 强经验可在编码前统一替换，但三端不要双栈 |
| 路由 | Next.js App Router | 文件路由、布局与按路由拆包统一；筛选条件仍显式写入 URL search params |
| 服务端状态 | TanStack Query | 缓存、失效、轮询和 mutation 生命周期明确 |
| 表单/校验 | React Hook Form + Zod | 配置表单性能好，可与生成类型边界校验配合 |
| UI | Ant Design（后台）+ CSS Modules/轻量自研聊天组件 | 快速完成表格表单；H5 避免携带完整后台组件库 |
| 状态机 | 原生 reducer；必要时 XState | P0 控制依赖，复杂恢复与并发状态可平滑升级 |
| API | OpenAPI 生成类型客户端 + 薄封装 | 统一三调用面、错误和契约，避免手写漂移 |
| 流式 | Fetch ReadableStream + SSE/NDJSON parser | 支持 POST、幂等键、HTTP 状态和渐进展示 |
| 测试 | Vitest、Testing Library、MSW、Playwright | 覆盖状态逻辑、API mock、三端 E2E 和多上下文 |
| 质量 | ESLint、Prettier、Stylelint、commit/CI 门禁 | 统一规范与自动阻断回归 |
| 监控 | 支持 source map、trace 关联和脱敏的前端监控平台 | 定位 H5 浏览器差异、流中断和发布故障 |

渲染策略不等于框架选择。P0 的商家端和运营端采用客户端交互为主；消费者 H5 可先输出静态页面外壳，再在客户端加载公开配置和会话。若上线前确认需要按商家生成动态分享元数据、搜索引擎收录或服务端首屏，则在同一 Next.js 技术栈内启用对应路由的服务端渲染。三端均不得用 Next.js 缓存跨用户复用含登录态或 Session 的响应；自托管多实例时需要单独验证缓存一致性与反向代理流式透传。

## 13. P0 与延期项

### 13.1 P0 必须完成

- 三个独立应用及 Public/Merchant/Operator API 边界。
- 商家单客服闭环：草稿、FAQ/文本/PDF、处理状态、试聊、发布、固定链接/二维码、回滚、暂停。
- 消费者匿名会话：创建/恢复、新建咨询、消息流式展示、稳定幂等重试、需求提交和联系入口。
- 同一 Session 顺序处理、刷新恢复、同源多标签基本同步和并发冲突收敛。
- 暂停、额度不足、限流、超时、流中断、Session 过期等显式状态。
- 商家咨询/需求/未解决问题查看与人工跟进状态。
- 平台商家/客服状态、试点额度、聚合用量、失败任务、基础模板和审计查看。
- 手机浏览器与微信真机兼容基线；安全渲染、脱敏监控与核心 E2E。

### 13.2 延期（P1/P2 或待确认）

- 多客服、多门店、商家团队协作、细粒度商家角色、复杂字段级草稿合并。
- Word/Excel/图片 OCR 等更多知识格式、大批量导入、实时任务 WebSocket 推送。
- 跨 Session 个人记忆、跨设备匿名身份迁移、离线历史、Service Worker 离线发送。
- 消费者多消息排队、真正的跨标签共享流连接、SharedWorker。
- 真人坐席、订单/库存/预约/支付/退款、全渠道消息与语音/数字人。
- 运营批量导出、批量操作、自定义角色、复杂计费套餐与在线支付。
- 商家自定义 CSS、插件式页面装修、多语言与完整国际化。
- SSR、搜索引擎商家公开页和依赖微信 JSSDK 的高级分享能力。

### 13.3 开工前需确认但不阻碍架构的事项

- 商家登录方式、账号找回与是否要求多因素认证。
- 30 分钟 Session 有效期、历史展示及各类数据保留时长。
- 首批行业与需求收集字段模板。
- PDF 大小、页数、并发上传和上下文长度限制。
- 联系方式类型以及留言后是否需要站内/外通知。
- 目标浏览器最低版本、监控平台和无障碍目标等级。
- 发布期间旧 Session 的最终版本策略，以及紧急信息失效是否强制结束旧会话。

## 14. 实施顺序建议

1. 先确定 OpenAPI/流事件/错误协议、设计 token 与三个应用骨架，建立依赖边界和 CI 门禁。
2. 纵向打通一条最小链路：公开配置 → 匿名 Session → 单条非流式消息 → 历史恢复，再升级为流式与错误收敛。
3. 完成商家草稿、基础知识、测试、发布及固定入口，让真实资料可驱动 H5。
4. 补齐 Session 过期、新建咨询、多标签、暂停、额度、限流和弱网异常。
5. 完成咨询管理、需求、运营用量/异常/审计，最后做真机兼容和端到端验收。

每阶段均应使用至少两个商家、多个匿名访客与多个浏览器上下文做隔离验证。任何页面完成不等于闭环完成；P0 退出条件是 A01–A14 对应关键路径在真实部署环境通过，并且前端没有把服务端失败表现为业务成功。
