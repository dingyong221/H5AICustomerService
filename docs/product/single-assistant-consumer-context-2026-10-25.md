# 每商家一个客服与消费者独立上下文

更新时间：2026-10-25（Asia/Shanghai）。用户本轮确认：每个商家只能有一个AI客服，修改始终维护这个客服；所有消费者咨询该客服，但每个消费者的上下文必须独立。本文是本轮实施基线，不代表已上线。

## 产品规则

1. 商家空间只有一个当前客服身份、一个固定消费者地址。初次创建后，基础资料、附件知识、名称、试聊、发布、历史版本、改善均修改同一个客服，不再新增其他客服。普通修改与重新发布不是新建产品。
2. 后台以“我的AI客服”为中心；已创建时不展示“新建客服”、列表选择和数量比较。各菜单直接进入该客服对应功能；旧创建链接、重复点击或并发请求进入原客服，不能覆盖原资料。
3. 客服身份与发布版本分离。同一客服可保留草稿和多个历史版本；沿用既定普通会话快照机制，紧急撤回仍能终止旧版本和在途回复，固定地址保持不变。
4. 消费者身份、会话、消息分离：商家→唯一客服→独立访客→会话→消息。服务端以商家/客服/访客凭证/会话四重作用域校验读取、续聊和发言；不同消费者共享客服业务知识，不共享私人问题、回答或上下文。
5. 匿名访客用现有HttpOnly Cookie识别；同IP、链接参数、相似问题都不是同一个消费者的证明。首版不假设跨设备识别，不引入消费者账号或设备指纹。
6. 同浏览器保存的仅是可恢复请求引用，不把访客密钥或完整会话授权令牌写入localStorage。刷新/关闭后返回可在有效期内恢复；主动“开始新咨询”、凭证丢失、到期或撤回时明确开始新上下文，不静默拼接旧对话。
7. 完整消息记录留服务端；模型只带本会话最近的完整问答轮次并限制总字数，避免无界增长或带入别人的记录。已有发送幂等、同会话单个在途问题、失败重试和历史恢复继续保留。

## 数据与兼容方案

新增商家→当前客服的一对一绑定，merchant_id为主键、客服通过复合外键约束属于该商家；创建事务先锁商家，再检查绑定，已有绑定就返回原客服，不修改其草稿。所有管理/知识/改善和公开会话查询均限定当前绑定，禁止通过旧ID绕过唯一性。

既有记录不删除。最新已核快照有17客服/16商家，其中一商家同时存在一份未发布草稿和一个已发布客服；迁移优先保留该已发布客服为当前客服，另一草稿保留历史原始数据且不再作为可管理/可咨询的第二客服。单商家多份已发布客服属于歧义，预检应停止并给出待选择清单，不自动合并价格、消息或发布链接。本轮部署前仍需现场重新核对，不能拿旧快照当最新事实。

已有已发布地址和会话不得因资料修改或绑定回填丢失。未发布历史地址仍不可咨询；不将历史草稿错误地变为公开链接。A6自助开通后续复用同一唯一绑定，不新增平行创建规则；其未合并迁移需在现有链后重新编号。

## 验收要求

- 同商家重复创建、不同幂等键并发创建、两个成员同时创建、手工创建与引导创建竞争，最终只绑定一个客服；输入重试不覆盖原资料，角色/跨商家越权仍拒绝。
- 已有商家直接进入原客服；旧创建地址回到当前客服，各功能不再要求选择客服；草稿、附件、试聊、发布、改名都保持相同ID与消费者地址。
- 同一客服下两个隔离浏览器上下文的消费者互不可读；伪造另一个会话ID、请求引用或跨商家信息不能恢复或发言。
- 多轮问答能使用本消费者前文；另一消费者的标记不会进入模型输入。刷新、关闭后返回、新标签页、重复发送、在途恢复、主动新咨询、过期和撤回分别验证。
- 模型上下文保留完整轮次且有预算；完整历史仍保留。清除当前浏览器恢复引用不等于删除服务端业务记录。
