# 标准版本 v0.1.0 产品验收闭环

> 评估基线：commit `c7f69cb`。当前静态评估结论：**NO-GO**。本文定义可执行的标准版本Definition of Done（DoD）与逐项证据，不表示真实WorkBuddy、托管MySQL、正式模型、远程环境或生产发布已经完成。

## 1. 版本目标与状态口径

标准版本v0.1.0只交付一条可解释、可恢复、失败关闭的主链：商家从WorkBuddy选择“生成AI客服”或“继续使用”，完成平台登录、WorkBuddy身份绑定、单一商家选择与consent后，生成一个可编辑客服草稿；已有客服可以进入受保护管理页；商家明确发布后，消费者通过固定公开H5链接咨询。

验收状态必须分成三层，不能互相替代：

| 状态                    | 含义                                                                           | 可以声明               | 不可以声明                      |
| ----------------------- | ------------------------------------------------------------------------------ | ---------------------- | ------------------------------- |
| `local_candidate`       | 本地MySQL、WorkBuddy提供方模拟器和确定性生成/回答适配器下，本文本地DoD全部通过 | “v0.1.0本地候选已验收” | “真实WorkBuddy已接通”“生产可用” |
| `external_integrated`   | 真实非生产WorkBuddy、托管私网MySQL和正式模型测试账号分别通过外部门禁           | “v0.1.0外部集成已验收” | “已经生产发布”                  |
| `production_releasable` | 前两层通过，并完成正式域名/TLS、Secret/KMS、监控告警、备份恢复和发布回滚门禁   | “v0.1.0可生产发布”     | 未经实际发布就声明“已上线”      |

标准版本v0.1.0的DoD是：第7节所有本地项目通过、第8节所有外部依赖项目通过，并且没有P0/P1阻断。只有本地项目通过时只能形成`v0.1.0-rc.N`候选，不能把版本状态写成正式可用。

## 2. 标准用户闭环

```text
WorkBuddy入口
  ├─ 生成AI客服
  │    └─ 登录 → 绑定 → 选择单一商家 → consent
  │         ├─ 当前商家0个客服 → 创建/恢复四步引导 → 明确确认 → 生成草稿
  │         └─ 当前商家已有客服 → 不重复“首次生成”，引导到继续使用
  │
  └─ 继续使用
       └─ 登录 → 绑定 → 选择单一商家 → consent
            ├─ 0个客服 → 提示尚未创建 → 切换生成入口
            ├─ 1个客服 → 返回该客服的受保护管理入口
            └─ 多个客服 → 明确选择一个 → 返回所选客服的受保护管理入口

受保护管理页 → 校验登录/Membership/客服归属 → 编辑与测试 → 明确发布
  → 不可变Release + 固定publicSlug → /a/:publicSlug公开H5 → 创建匿名Session并咨询
```

登录、绑定、选择商家、consent、生成和发布是六个独立事实。前一步成功不能被页面、模型或Skill自动解释为后一步也成功。

## 3. WorkBuddy两段式入口契约

### 3.1 “生成AI客服”

- 入口意图为`create_customer_service`，面向尚无客服的当前授权商家。
- 先完成平台账号登录、WorkBuddy外部身份绑定、单一商家确定与Connector consent；聊天不收集密码、OTP、Token、`open_id`或`merchant_id`。
- 当前商家没有客服时，创建或恢复该账号/商家唯一的未完成onboarding流程；刷新、暂停和重新授权后能从服务端事实恢复。
- 当前商家已有客服时，v0.1.0不创建第二个“首次客服”，而是明确提示已有客服并引导到“继续使用”。“新增更多客服”是后续能力。
- 确认前只保存已验证输入；确认后生成可编辑草稿，不自动测试、不自动发布、不自动得到线上H5。

### 3.2 “继续使用”

- 入口意图为`open_management_console`，只查询当前已授权商家的客服，不接受工具参数自报商家或客服归属。
- 0个客服返回`start_first_onboarding/no_assistant`，不构造管理链接。
- 1个客服返回该客服的安全摘要和管理入口；入口不含Token、授权码、`open_id`、原始商家ID或登录Cookie。
- 多个客服返回用户可理解的客服名称、状态和不透明候选引用，不默认选择。用户明确选择后，服务端再次校验候选仍属于当前商家，才返回所选客服入口。
- 多客服列表不能只有难以识别的内部引用；至少提供经过服务端确认的展示名与状态。选择动作不得接受列表外任意ID。

## 4. 身份、商家与consent门禁

页面和MCP必须遵循同一顺序：

1. **平台登录：** 只由服务端session确认Account；query、callback文本、localStorage和环境变量状态不能确认登录。
2. **WorkBuddy身份绑定：** 只由第三方应用OAuth服务端换票取得`open_id`并立即转换为HMAC查找键；Connector OAuth Token与WorkBuddy Open API Token不得混用。
3. **商家分支：** 0个有效Membership停止；1个商家可以预选但仍需consent；多个商家不默认选择且一次只授权一个。
4. **Connector consent：** 展示Connector、单一商家、`mcp:tools`和四个实际工具动作；同意/拒绝必须由服务端事务记录。
5. **平台MCP Token：** 只在上述事实全部通过后签发；每次工具调用继续复核grant、Membership和对象归属。

任何后端状态源或安全操作路由缺失时，Merchant Web保持`backend_unavailable`或对应禁用状态。URL里的`code`、`state`、`error`、`connected=true`和商家/客服参数最多触发固定“未采信”提示，不能推进流程。

## 5. 生成、管理、发布与公开H5契约

### 5.1 生成草稿

四步输入固定为行业、业务资料、售卖策略/资料不足规则、确认生成。DoD要求：

- 服务端在确认前再次计算缺失项；资料不足时保持可编辑，不进入`generating`。
- 同一确认操作使用幂等键；成功、失败或响应未知都不能重复创建客服。
- 生成器只接收已确认事实，输出一个`Assistant`和一个可编辑`AssistantDraft`；不得补造价格、优惠、联系方式或能力范围。
- 只有服务端内部生成协调器能写入`generation_succeeded/failed`；浏览器、Skill和MCP调用方不能自报生成成功。
- 正式生成器未配置时返回`GENERATION_UNAVAILABLE`，流程保持可恢复且数据库中没有新客服。

### 5.2 管理链接

- 链接只负责定位，不负责授权；打开后必须验证平台登录、活动Membership、当前grant和客服归属。
- 链接可包含服务端签发的不透明客服引用，但不能包含Bearer、Refresh Token、授权码、`open_id`、密码、OTP或原始身份查找键。
- 复制给另一账号、撤销Membership后重放或替换客服引用均不能读取目标客服；对无权资源返回安全404/拒绝，不泄露是否存在。
- 管理页必须读取真实服务端草稿、发布检查和当前Release，不能继续展示静态“待连接”占位并称为已完成。

### 5.3 发布与公开H5

- 生成完成仍是草稿。只有用户在管理页通过发布检查并明确确认，服务端才创建不可变Release并切换活动版本。
- 同一客服的`publicSlug`稳定；发布新版本不改变公开URL。未知、未发布、暂停或无活动Release统一显示安全不可用状态。
- `/a/:publicSlug`加载真实商家/客服显示名、业务范围、欢迎语与活动Release；不得暴露内部merchant/assistant/release ID。
- 首条消息创建绑定匿名访客凭据、商家、客服和Release的Session；相同客户端请求幂等，跨访客与跨商家替换ID均失败。
- 本地验收可以使用确定性规则/模型适配器回答固定FAQ和资料不足问题，但必须产生真实服务端Session、Message和追溯事实；静态前端文案不是公开H5验收证据。

## 6. 验收环境与证据包

### 6.1 本地验收环境

本地DoD使用以下受控依赖，验证产品闭环而不冒充外部完成：

| 依赖      | 本地验收方式                                      | 必须证明                                                      |
| --------- | ------------------------------------------------- | ------------------------------------------------------------- |
| WorkBuddy | 独立提供方模拟器 + 官方MCP SDK测试客户端          | 两种OAuth域隔离、回调/state、两段入口、四工具和失败映射       |
| MySQL     | 可销毁的本地MySQL InnoDB实例，执行正式迁移        | 事务、唯一约束、幂等、租户隔离和重启后恢复；不能用内存Map代替 |
| 生成/回答 | 确定性生成器与确定性回答适配器                    | 创建真实草稿/Session/Message，不补造事实，异常可重复注入      |
| Web       | Merchant Web与Consumer H5生产构建，以本地HTTP运行 | 页面读取真实本地API；禁用骨架不能算通过                       |

仓库必须提供单一入口`pnpm acceptance:v0.1.0`（名称可等价，但需在根脚本可发现），负责准备夹具、运行迁移、启动依赖、执行浏览器/API/MCP验收并清理。仅有分散单元测试不能关闭标准版DoD。

### 6.2 证据包格式

每次候选验收生成`artifacts/acceptance/v0.1.0/<UTC时间>-<commit>/`或等价的CI不可变附件，至少包含：

| 证据ID        | 内容                                                                           | 脱敏要求                                          |
| ------------- | ------------------------------------------------------------------------------ | ------------------------------------------------- |
| `EV-MANIFEST` | commit、Node/pnpm版本、迁移版本、环境类型、测试夹具ID、命令和开始/结束时间     | 不含Secret和真实个人身份                          |
| `EV-CHECK`    | `pnpm format:check`、`pnpm check`、`pnpm build`及单入口验收的完整退出码        | 失败日志不能截去首个根因                          |
| `EV-UI`       | 两段入口、登录/绑定/商家/consent、四步生成、0/1/多客服、管理与公开H5截图或视频 | 遮蔽Cookie、Token、授权码和个人信息               |
| `EV-HTTP`     | MCP、授权状态、生成、管理、发布和Public API的脱敏请求/响应摘要                 | 删除Authorization、Cookie、code、state、`open_id` |
| `EV-DB`       | 验收前后关键行数、租户键、版本、幂等记录和Release/Session归属断言              | 仅使用测试ID；不导出正文Secret                    |
| `EV-TRACE`    | 每个主场景的request/trace ID与审计动作结果                                     | 不记录Token、密码、OTP或HMAC原料                  |
| `EV-SEC`      | 工具Schema、URL、日志、前端产物和审计的敏感词/跨租户负向扫描                   | 原始命中需先脱敏再归档                            |
| `EV-EXT`      | 外部WorkBuddy、托管MySQL和正式模型门禁记录                                     | 只记配置ID/版本、时间与结果，不归档凭据           |

证据必须来自同一commit和同一验收运行。测试文件存在、类型检查通过或手工描述“看起来正常”都不是端到端通过证据。

## 9. 当前结论与最短关闭路径
