# R1 受控 Web 变更方案

状态：候选准备，非执行授权。目标是现有受控 Web 试用站，不扩大为正式商用。先通过统一提交的 CI、隔离预发布及升级兼容检查；生产高影响迁移和切换另由项目负责人确认。

## 现有环境和变更范围

公网入口为 `h5cs.1rying.com`，服务器 `114.132.92.111`。只读核对的 merchant／worker 修订为 `acfbb34`，API／consumer 为 `99ea6701`，ops 为 `19f7c540`。生产 MySQL healthy，Schema 共三十张表，包含一张迁移记录表，未映射宿主 3306。没有执行候选迁移。

本轮包括改进任务、FAQ 修正、原题复测、人工判定及版本关联，人工联系说明、资料缺项提醒，以及保存／重新确认反馈和幂等重放授权修复。

不启用 WorkBuddy／MCP／OAuth，不新建收费资源、不更换模型密钥、不删除商家、草稿、发布、消息或回退镜像。离机备份仍遵循仅限受控试运行的既有风险接受，不作为正式生产备份合格证明。

## 源码和制品放行条件

统一分支为 `codex/merchant-improvement-loop`，基于 `53172bd`，包含尚待收敛的商家后台和独立 Skill 基础提交。最终 SHA 由本次 PR 冻结，不复用旧流水线或旧镜像的通过状态。

五个应用镜像必须来自同一最终 SHA，路径模式为 `same_domain`，记录完整摘要与来源校验。没有新的制品证据前，不把服务器源码重建描述成已完成签名镜像链。此次不覆盖既有版本标签。

本机 Node 25 的局部验证不是 Node 24／Linux／Docker 发布门禁；最终 CI 应覆盖统一类型、单测、锁定依赖、安全例外、构建、路由和浏览器流程。

## 数据变更和停点

增量迁移 `0012_chilly_talisman.sql` 只新建 `assistant_improvement` 和 `assistant_evaluation_run`，索引与外键均作用于新表。不重写已有业务行，没有 DROP、TRUNCATE 或旧表字段删除。

- SQL SHA256：`1fd4e574c6d7eea52a0625c99705c34c52dc0c13264964f7cb104d2f5af045a8`。
- 当前十三条迁移完整计划 SHA256：`9893710d77929551c9cf361e3f9a69554f529b4536beb4ff5a8cf762d7b3e17f`。

执行前必须重新核对最终镜像中的计划、目标 DNS、库、TLS、既有迁移记录、容量及受限迁移凭据，并记录本次变更和备份／受控试运行风险引用。任一摘要或目标不符就停止。

隔离空库十三条迁移和十三项真实业务集成已通过；这不是现有生产库升级成功证明。预发布应验证旧 Schema 增量升级，并核对已有商家、草稿、正式快照与消息不变。

现有 Drizzle 迁移器按最后一条 `created_at` 决定后续执行范围，不会自行核验全部历史 SQL 摘要。执行前必须将实际 `__drizzle_migrations` 按时间和 ID 排序，逐项对照候选镜像前十二条 SQL hash 与 journal 时间；不能只核对数量或最后一项。任一缺项、漂移或异常顺序均停止，不手改迁移记录“补齐”。新增表的外键还可能取得已有父表的 metadata lock，不能把新增表描述为完全无运行影响。

MySQL DDL 不保证整条迁移事务回滚。失败后先只读核对已落地的表、约束和迁移记录，不盲目重跑，不用删表“反向回滚”。

## 发布顺序和运行保护

1. 在 CI 构建和验证，不在磁盘已用约 94% 的业务机重复全量构建。
2. 拉取前核对压缩层、共享层、磁盘和内存余量；无法保留可靠运行及回退余量时停止，由负责人选择明确的清理范围或扩容，不擅自清理旧栈。
3. 在独立 staging 数据与回环端口完成升级、真实模型闭环、双商家隔离、老客户端兼容、失败恢复和回退检查，不连接生产库测试。
4. 生产变更获确认后，在受控维护窗口由网关阻止新的消费者会话／消息及商家写入／试聊，保留已有任务结果的只读查询。旧 Worker 继续运行；核对 `conversation.turn` 的 pending、processing 数量以及会话 `active_turn_id` 均归零，再停止旧 Worker。最多观察 120 秒；未归零就不停止、不切换，保持原版本并核对原因。`PollLoop.stop()` 会中断正在执行的模型请求，不能用 SIGTERM 或 Docker stop 代替自然排空。
5. 迁移验证后切换 Worker，再切 API、消费者与管理页面。不同版本 Worker 不应同时消费同一个生产队列；旧 Worker 必须先完成已有任务并停止领取。
6. 新旧客户端以 `X-H5CS-Features: human-contact` 协商字段。新 H5 可接旧 API，旧 H5 在新 API 上仍收到原字段集合；Worker 必须先兼容新旧草稿。
7. 对新提示和模型策略使用独立版本标记，例如 `merchant-r1-boundary-v1` 与 `qwen-plus-r1-v1`，商家发布与改进判定使用同一配置。旧快照保持不变。
8. 仅核对本项目 Host 的新槽路由，先检查 Nginx，再受控切换。验证健康、创建／确认／试聊／发布、消费者新旧会话、改进与双租户隔离，再解除维护并观察。

正式端口在执行前只读核对占用，不把旧候选端口直接当作可用。生产私钥、数据库连接串、模型密钥和内部调用凭据均留在受限环境，不进入 PR、日志或 Skill。

## 回退边界

切换前记录五个原镜像、环境引用及 Nginx 文件摘要。应用回退保留新增表、改进历史和已发布快照，不回退用户业务行。

旧商家代码没有人工联系说明字段。新记录写入后，不能未经验证就恢复旧版编辑写入，否则旧解析器可能丢弃新字段。预发布必须验证这一边界；不兼容时保持受控只读维护并修复前进，不能用旧页面覆盖新配置来假装回退成功。

当前没有应用级全写入只读开关。若回到旧 merchant，必须在网关覆盖全部商家路径和 `/console` 兼容路径的写请求，包括 Next Server Action POST；仅隐藏按钮无效。登录、退出等 POST 同样受维护限制，不能承诺维护期间仍能重新登录。恢复商家写入必须使用已验证保留新字段的版本。新旧 Worker 对同一个数据库没有按版本分队列的机制，任何时候不能把两个版本同时接入该生产队列。

数据库损坏或隔离异常先停止写入、保存证据，再决定恢复；不自动切回或删除新表。回退检查未通过，不进入生产切换。
