# 字段与帮助

## 最少资料模型

下表是对话层的资料主题，不是尚未实现的工具 Schema。字段名仅用于解释和评审，不能当作已落地 API。

| 主题       | 要收集的内容                               | 追问原则                                                     |
| ---------- | ------------------------------------------ | ------------------------------------------------------------ |
| 商家与客服 | 已授权商家、客服名称                       | 商家只能来自服务端授权上下文；客服名称可让用户提供或确认建议 |
| 业务描述   | 主要卖什么/提供什么服务、服务谁            | 先用一句开放问题；过宽时只追问一个区分问题                   |
| 细分行业   | 基于业务描述整理出的候选                   | 必须让用户确认；不得把行业常识当商家事实                     |
| 业务条目   | 名称、核心说明、适用对象                   | 至少一项；规格、套餐、区域、交付方式按需问                   |
| 价格       | 金额、币种/单位、起步条件                  | 未提供、确认暂无、暂时跳过必须分开                           |
| 优惠与策略 | 套餐、折扣、赠品、阶梯价、会员/渠道/区域价 | 同时收集适用条件和有效期；未知则标缺失                       |
| 服务规则   | 营业时间、服务区域、限制条件、无法承诺事项 | 不根据行业自动补齐                                           |
| 问答资料   | 常见问题、真实答案、无法回答时的处理方式   | 用户事实与系统建议分开展示                                   |
| 联系方式   | 用户愿意公开给消费者的正式联系入口         | 不把登录手机号或绑定信息自动作为公开联系方式                 |

## 字段状态

对会影响真实业务回答的资料，至少区分：

- **用户已提供**：记录原意，可整理措辞但不能改变事实。
- **用户确认暂无**：用户明确表示不存在该项。
- **尚未提供**：还没有答案，不能推断为“无”。
- **暂时跳过**：用户主动跳过；在预览中说明影响。
- **系统建议**：由系统提出，必须与用户事实分区并等待确认。

不要用空字符串或模型猜测把这些状态混为一谈。

## 每轮提问方式

每次回复尽量包含：

1. 当前步骤和简短进度。
2. 为什么需要当前信息。
3. 一个主要问题。
4. 1～2 个简短示例，但明确示例不是用户事实。
5. 可用操作：“修改”“跳过”“帮助”“取消”。

示例：

> 当前在补充价格与售卖规则（第 3/5 步）。这些信息会影响客服能否准确报价。请告诉我主要商品的价格和单位，例如“基础套餐 199 元/月”；如果暂时没有，可以回复“确认暂无”或“暂时跳过”。

## 帮助响应

用户说“帮助”“为什么要问”“给个例子”时：

- 解释当前字段用于哪类客服回答；
- 说明是否为创建草稿所需、跳过后会怎样；
- 给出格式示例，并标注“仅为示例”；
- 提醒真实价格、优惠、库存、营业规则和承诺必须由用户确认；
- 不保存示例为业务事实，不触发创建，不改变当前工作流状态。

若用户问“为什么要登录/绑定”：

> 登录和授权用于确认你能访问哪个商家及客服。请只在平台安全网页完成登录或验证码校验，不要在聊天中发送密码、短信验证码或访问令牌。

若用户问“为什么没有直接发布”：

> 本流程只创建可编辑草稿，避免未经核对的价格、优惠或业务承诺直接面向消费者。发布需要单独的预览、权限检查和明确确认；当前 Skill 源稿不执行发布。

## 不应在对话中收集的字段

不得定义、索取、转发或复述以下内容：

- 密码、短信验证码、OTP、TOTP；
- Access Token、Refresh Token、API Key、Client Secret、私钥；
- 用户自报的 `open_id` 或其他用于认领账号的内部标识；
- 完整支付卡、身份证件或与本流程无关的敏感个人信息；
- 登录手机号作为公开联系方式，除非用户在平台安全页面另行明确配置。
