The positive text PDF is constructed in material-parser.test.ts using standard
PDF objects and a valid byte-offset xref. It has no external assets or URLs.
Adversarial ZIPs are generated in memory in the same test: there is no downloaded
malware, no executable macro payload and no network access needed by the tests.

Verified local platform: Windows x64, @kreuzberg/node 4.10.2 native bindings.
The same non-mocked tests must also pass on the Linux CI/runtime; Windows-only
success is not evidence that production's libpdfium.so packaging is complete.
Native extraction configuration and format claims were checked against:
https://docs.kreuzberg.dev/reference/api-typescript/
https://docs.kreuzberg.dev/reference/formats/
https://github.com/kreuzberg-dev/kreuzberg-lts/blob/v4.10.2/crates/kreuzberg-node/src/config/types.rs
In 4.10.2, JsSecurityLimits keys are camelCase. Its generic archive limits are
supplemented by our independent bounded OOXML decompression/CRC/subtype checks.
V8 --max-old-space-size does not cap native Rust/PDFium allocations: actual
container memory/PID/CPU limits and the parent-enforced timeout remain necessary.
The read-only production image must pre-extract the pinned bundled PDFium to
/app/parser-runtime/kreuzberg-pdfium/libpdfium.so at build time; only the owned
Linux child is given TMPDIR=/app/parser-runtime when that fixed file exists.
This preserves /tmp:noexec and avoids writable executable runtime caches.
